# Running Wrapped

A Spotify-Wrapped-style running analytics app: runners import workout files and get
weekly / monthly / yearly recaps, progress analytics, and optional AI-written summaries.
"See how far you've come. Your running journey, beautifully told."

## Repo layout

## How we work: learning mode (important)

The developer is an experienced engineer (Go, Node.js, TypeScript, React, PostgreSQL)
**learning professional Java + Spring Boot** with this project. React/TS needs less explanation; Java/Spring needs more.

- **Never one-shot.** Work one roadmap step at a time. Each step should be a small, reviewable diff
  that compiles, passes tests, and can be run. Stop at the end of a step and summarize; don't roll into the next one.
- **Explain Java/Spring decisions as you make them.** Briefly say *why*, and compare to Go/Node where it helps
  (e.g. "a Spring bean is roughly a singleton you'd wire by hand in `main.go`"). Skip explaining things a senior TS/Go dev already knows.
- **Offer "your turn" exercises.** When a step has a small, well-scoped piece (a repository method, a DTO, a test),
  offer to let the developer write it and then review it (`/java-review`) instead of writing it yourself.
- **Prefer the boring, idiomatic option.** No abstractions, patterns, or libraries "for later". If you think something
  is worth adding, propose it and explain the tradeoff. Don't add it without asking.
- After finishing a milestone, tick it in `docs/ROADMAP.md` and add the key concepts to `docs/learning/LEARNING_LOG.md`.

## Non-negotiable product constraints

- **No Strava API integration** until its developer agreement has been reviewed and the use (analytics/AI) is confirmed allowed.
  MVP data comes from manual FIT / GPX / TCX file import only. Keep an extension point for providers, but don't build one.
- **AI is opt-in.** Never send workout or health data to an LLM provider unless the user has explicit, recorded consent.
  The LLM only *narrates precomputed statistics*. All math happens in our code.
- **No unsupported claims.** Don't present a single metric as proof of improved fitness. Never derive a distance PR
  (e.g. fastest 5K) from a longer run's average pace. Only use a real best-effort segment from the time series.
- **Health data is sensitive.** Don't log it, don't put it in error messages, and scope every query to the authenticated user.
- Modular monolith. **No microservices**, no message brokers, no Kubernetes.

## Cross-cutting conventions

- Store canonical units: **meters, seconds, UTC `Instant` + IANA timezone**. Convert to miles/km and local time only at the edges (API response formatting or UI).
- API is REST under `/api/v1`, JSON, errors as RFC 9457 Problem Details. The OpenAPI spec generated by the backend is the
  contract, and mobile TS types are generated from it. Don't hand-write duplicate types.
- Secrets only come from environment variables. Never commit `.env` files or keys.
- **Commit and push at the end of every completed roadmap step** (after tests pass), one focused commit per step with conventional-ish messages (`backend: add users migration`). Never commit a failing build.
